# MongoDB数据库详细设计

本文以集合约束、索引定义、服务代码和原始测试记录为依据，说明文档结构为何如此组织、如何读写、哪些一致性由数据库提供、哪些依赖应用流程。

全文以三项设计理由为主线，按设计依据、访问模式、模型、字段、嵌套、状态、冗余、约束、索引、事务、查询、安全、兼容、两项选型说明及验证十六部分组织。

## 一 为什么这样设计

本设计由“如何使用数据”决定，而不是因为使用MongoDB就随意组织字段。先区分账号认证、可变问卷、不可变发布、未完成输入和正式答卷，再为每种生命周期选择文档粒度、关系与一致性边界。

| 需求 | 设计选择 | 为什么这样选择 | 代价与保证方式 |
| --- | --- | --- | --- |
| 账号可创建多份问卷、多端登录 | users与sessions独立，问卷引用owner_id | 避免重复账号资料，支持会话退出和过期 | 引用检查由服务执行；TTL不代替即时到期判断 |
| 创建者持续编辑，旧答案不能变含义 | surveys草稿与survey_versions快照分开 | 可变状态与历史事实分开，旧过程绑定原版本 | 发布复制定义，有存储成本；指针和快照事务更新 |
| 题目、限制、条件一起解释 | 嵌入definition | 完整问卷通常一起读取和发布，不为每个条件节点往返拼装 | 文档必须有界；最多100题及选项规模限制 |
| 提交数量持续增长 | responses独立 | 不把所有答案追加到单一问卷数组，便于分页和聚合 | 仍有问卷级协调写热点，不等于无限吞吐 |
| 中间输入可能不合法但需要恢复 | attempts独立 | 草稿可保存“-”，正式答案保持完整合法；统计不混入未完成数据 | 增加状态机和原子提交，终态清空内容副本 |
| 同账号并发进入 | 部分唯一索引 | 一问卷一账号只有一份进行中过程，不被版本和匿名切换绕开 | 状态变更需正确，结束后释放名额 |
| 旧请求不能覆盖新输入 | revision条件更新 | 检查客户端基于哪次保存，发现冲突不静默覆盖 | 前端要保留输入并提示重载 |
| 结果含义与查询都要清楚 | 有限冗余version、path、关联键 | 从同一可信来源生成，筛选与复核方便 | 不能由客户端任意拼写，需要事务和回归 |
| 数据形状、唯一性、跨文档一致都要保证 | schema、索引与事务分工 | 文档灵活不等于取消约束 | 复杂语义、引用、权限仍由后端检查 |

因此，本系统不用一个大集合保存所有对象，不把题目全部拆成独立集合，也不让草稿与正式答卷混用。保留的冗余必须有来源和用途，生命周期结束后不继续维护两套答案。下面各节给出选择对应的字段、查询与实现证据。


## 二 业务需求与访问模式

数据库设计首先服务于实际操作，而不是先规定若干“表”再填字段。一个问卷定义读取频繁、结构有界；答卷持续追加、数量不预先确定；发布快照应保持旧含义；未完成输入允许暂时不合法，因此四类数据不能混为同一生命周期。

| 场景 | 主要读取 | 主要写入 | 需要保证 |
| --- | --- | --- | --- |
| 注册、登录、退出 | users、sessions | users、sessions | 账号规范化唯一；密码不明文存储；会话过期即时拒绝 |
| 查看自己的问卷 | surveys，当前页问卷的responses计数 | 无 | owner_id隔离，分页按创建时间倒序 |
| 保存创建者草稿 | surveys的归属与revision | surveys.draft、revision、updated_at | 同窗口慢响应和多窗口修改不静默覆盖 |
| 发布 | surveys.draft、现有版本序号 | survey_versions及surveys指针、状态、截止 | 发布快照与指针一起成功或回滚 |
| 开始或恢复填写 | surveys、survey_versions、attempts、必要的历史responses | 新建attempts及问卷协调字段 | 原版本和匿名选择保持；一账号一问卷一份进行中草稿 |
| 自动保存 | 本人attempts、绑定版本、当前surveys | attempts、surveys.activity_seq | 允许中间输入；revision检查；关闭与保存协调 |
| 正式提交 | 过程、绑定版本、问卷状态、历史答卷 | responses、attempts、surveys.activity_seq | 完整校验、禁止重复策略、幂等和事务一致性 |
| 放弃 | 本人attempts | 单个attempts文档 | revision匹配；内容清空后不能被晚到保存复活 |
| 整卷或单题统计 | survey_versions与筛选后的responses | 无 | 仅正式答卷；人数与次数区分；版本独立解释 |

同一账号允许多次正式填写，但最多保留一份进行中草稿。允许匿名并不取消登录要求，匿名是结果展示与存储直接身份字段的策略，不是一个共享匿名账号。

## 三 总体文档模型与关系

```text
users
 ├─ sessions.user_id
 └─ surveys.owner_id
       ├─ survey_versions.survey_id
       │    └─ definition.questions[]
       │         ├─ options[]
       │         ├─ validation{}
       │         └─ routing.rules[].condition{}
       ├─ attempts.survey_id + version_id
       │    ├─ raw_answers{} / current_question_id / revision
       │    └─ response_id ──→ responses._id（提交成功后）
       └─ responses.survey_id + version_id
            ├─ answers[{question_id,value}]
            └─ path[question_id]
```

箭头表示应用维护的引用，不是MongoDB外键。不存在自动级联删除，也不会仅因为声明了owner_id就自动校验用户存在。创建、发布、填写与统计服务按权限和业务规则维护关系，schema主要约束文档形状。

| 集合 | 文档粒度 | 增长方式 | 主要权威数据 |
| --- | --- | --- | --- |
| users | 一个账号 | 随注册增加 | 用户名、认证哈希 |
| sessions | 一次有效会话 | 登录增加、退出删除、过期清理 | 会话摘要与到期时间 |
| surveys | 一份问卷 | 创建时增加，持续更新 | 当前草稿、状态、截止、最新版本指针 |
| survey_versions | 一次发布 | 追加 | 该次发布定义和规则含义 |
| attempts | 一次填写过程 | 过程追加，进行中持续更新 | 已保存原始输入、绑定版本、过程状态 |
| responses | 一次正式提交 | 有效提交追加 | 规范化答案、实际路径与提交时间 |

业务ID由`uid()`生成24位十六进制字符串。schema对ID允许1～64位字母、数字、下划线或连字符，所以“数据库允许的格式”和“当前应用实际生成格式”不是同一范围。日期使用UTC和BSON毫秒精度；接口和页面可转换为本地时区，不把本地时间字符串作为数据库日期替代品。

## 四 六个集合的完整字段设计

以下“DB必需”逐项来自实际schema；“应用初值或来源”说明程序如何生成，不表示MongoDB自动填默认值。应用写入时必须完整提供必需字段。未设定通用删除、改名或密钥轮换接口，不把这些能力当作已经实现。


### 4.1 users

账号数据与问卷分离，避免每次创建问卷重复复制用户名和密码资料。注册写入用户，登录按username_key查询；管理问卷通过owner_id引用用户。

| 字段 | BSON类型及数据库约束 | DB必需 | 含义 | 应用初值或来源 | 更新与生命周期 |
| --- | --- | --- | --- | --- | --- |
| `_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 用户稳定标识 | uid()生成24位十六进制字符串 | 创建后不修改 |
| `username` | string；长度:3～40 | 是 | 展示和登录用户名 | 注册请求；3～40字符 | 当前无改名接口 |
| `username_key` | string；长度:1～200 | 是 | casefold规范化登录键 | 由username.casefold()计算，无数据库默认值 | 与用户名共同生成，唯一索引约束 |
| `password_hash` | string；长度:1～1024 | 是 | Argon2密码哈希 | passwords.hash()生成；不保存明文 | 仅用于服务端密码验证 |
| `created_at` | date | 是 | 注册时间 | now()生成UTC毫秒时间 | 创建后保留 |
| `schema_version` | int/long；值=1 | 是 | 用户文档结构版本 | 应用写入1 | 当前数据库仅接受1 |

用户注册时间用于追溯；username_key与展示名称分别保存，避免大小写差异绕过唯一性。当前没有改名流程，因此没有宣称已处理用户名变更同步。密码哈希只用于验证，不向前端返回。

**文档示例**

```json
{
  "_id": "111111111111111111111111",
  "username": "Student_A",
  "username_key": "student_a",
  "password_hash": "$argon2id$示意哈希不可用于登录",
  "created_at": {
    "$date": "2026-10-20T09:00:00Z"
  },
  "schema_version": 1
}
```

示例中的哈希字符串仅展示字段位置，不是可使用的Argon2凭据。真实数据由密码库生成符合算法格式的哈希，不能将示意文档用作登录种子。

### 4.2 sessions

登录会话与用户分开，使同一账号可有多个会话，并支持只退出当前会话。退出按token_hash删除对应记录，不删除用户。

| 字段 | BSON类型及数据库约束 | DB必需 | 含义 | 应用初值或来源 | 更新与生命周期 |
| --- | --- | --- | --- | --- | --- |
| `_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 会话记录标识 | uid()生成 | 退出时随记录删除 |
| `token_hash` | string；匹配`^[a-f0-9]{64}$` | 是 | 客户端会话令牌SHA-256摘要 | 摘要为64位十六进制；令牌本体只发给客户端 | 按摘要查询/退出删除 |
| `user_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 关联users._id | 认证成功用户ID | 引用关系由应用维护 |
| `expires_at` | date | 是 | 会话失效时间 | 创建时now()+7天 | 接口即时校验；TTL随后清理 |

会话令牌使用安全随机值生成；数据库只保存SHA-256摘要。TTL到期删除是后台清理，认证接口仍显式查询expires_at > now()，不依赖记录何时实际消失。

**文档示例**

```json
{
  "_id": "888888888888888888888888",
  "token_hash": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc",
  "user_id": "111111111111111111111111",
  "expires_at": {
    "$date": "2026-10-27T09:00:00Z"
  }
}
```

示例token_hash已替换为固定脱敏值；实际值必须从客户端持有的真实随机令牌计算，不能把示例摘要当作登录凭证。

### 4.3 surveys

一份文档保存问卷当前管理状态与可编辑草稿。公开填写摘要读取当前发布快照，不直接把正在编辑的draft当作已发布题目。

| 字段 | BSON类型及数据库约束 | DB必需 | 含义 | 应用初值或来源 | 更新与生命周期 |
| --- | --- | --- | --- | --- | --- |
| `_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 问卷稳定标识 | 创建时uid() | 各版本和答卷共同引用 |
| `owner_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 创建者引用 | 从当前登录用户读取 | 所有管理查询核对 |
| `share_code` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 填写链接中的随机分享码 | uid()生成，唯一索引 | 不等于访问权限；填写仍需登录 |
| `status` | 枚举；值=draft,published,closed | 是 | 问卷级开放状态 | 初始draft；发布后published；关闭为closed | 每次写操作按业务检查；发布可重新开放 |
| `draft` | object | 是 | 创建者当前可修改定义 | 初始标题、空说明、两项策略false、空题目列表 | 保存整体替换draft，不修改既有版本 |
| `deadline` | date/null | 是 | 当前统一截止时间 | 初始null；发布请求提交时区明确的日期 | 保存草稿不更新；发布更新 |
| `revision` | int/long；数值:1～未额外限制 | 是 | 创建者配置的乐观并发版本 | 初始1 | 保存草稿、发布、关闭递增；普通填写不递增 |
| `current_version` | int/long；数值:0～1000000000000000 | 是 | 最新发布版本号 | 初始0表示未发布 | 发布时+1；草稿保存不增加 |
| `created_at` | date | 是 | 创建时间 | 创建时now() | 列表按该字段倒序 |
| `updated_at` | date | 是 | 管理配置最后更新时间 | 创建、保存草稿、发布、关闭时now() | 普通提交/自动保存不更新此字段 |
| `activity_seq` | int/long；数值:0～1000000000000000 | 是 | 问卷级事务冲突协调字段 | 初始0 | 新填写开始/保存/提交、旧提交、发布、关闭递增；不是答卷数 |
| `schema_version` | int/long；值=1 | 是 | 问卷文档结构版本 | 应用写入1 | 与发布次数无关 |

revision用于创建者并发修改，activity_seq用于问卷级事务冲突协调，current_version用于选择快照，三者不能替代。updated_at也不是答卷提交时间或最近填写时间。下面示例是刚创建时的状态，发布后的指针变化见生命周期章节。

**文档示例**

```json
{
  "_id": "333333333333333333333333",
  "owner_id": "111111111111111111111111",
  "share_code": "abcdefabcdefabcdefabcdef",
  "status": "draft",
  "draft": {
    "title": "课程学习与实践调查",
    "description": "",
    "allow_anonymous": false,
    "allow_repeat": false,
    "questions": []
  },
  "deadline": null,
  "revision": 1,
  "current_version": 0,
  "created_at": {
    "$date": "2026-10-20T09:10:00Z"
  },
  "updated_at": {
    "$date": "2026-10-20T09:10:00Z"
  },
  "activity_seq": 0,
  "schema_version": 1
}
```

### 4.4 survey_versions

每次发布追加完整定义，使已经开始或已提交的答案保持原题目语义。定义不依赖随后对草稿的修改，也不需要依赖可变题目表重建历史。

| 字段 | BSON类型及数据库约束 | DB必需 | 含义 | 应用初值或来源 | 更新与生命周期 |
| --- | --- | --- | --- | --- | --- |
| `_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 发布快照标识 | 发布事务内uid() | attempts和responses引用 |
| `survey_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 所属问卷引用 | 发布的surveys._id | 配合version唯一 |
| `version` | int/long；数值:1～未额外限制 | 是 | 问卷内部发布序号 | surveys.current_version+1 | 从1开始；不等于schema_version |
| `definition` | object | 是 | 该版本完整问卷定义 | 从当次draft复制 | 当前API不提供修改/删除，管理员直写不受此业务约定保护 |
| `schema_version` | int/long；值=1 | 是 | 快照结构版本 | 固定1 | 格式识别 |
| `rule_engine_version` | int/long；值=1 | 是 | 规则解释语义版本 | 固定1 | 当前仅支持1，不代表已经实现未来迁移 |
| `published_at` | date | 是 | 发布时间 | 事务内now() | 历史版本展示与审计 |

不可变是当前API与服务的约定；schema本身没有禁止管理员直接更新该文档。version是该问卷的发布序号，schema_version和rule_engine_version是格式/语义识别号，应用1.1.0不意味着它们都应写成1.1.0。

### 4.5 attempts

持久化填写过程，以受限原始输入支持不完整保存。当前用户通过问卷范围HMAC键识别自己的过程，不需要向创建者暴露未提交内容。

| 字段 | BSON类型及数据库约束 | DB必需 | 含义 | 应用初值或来源 | 更新与生命周期 |
| --- | --- | --- | --- | --- | --- |
| `_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 持久化填写过程标识 | 开始时uid() | 新流程提交时同时作为responses.attempt_id |
| `survey_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 所属问卷引用 | 根据share_code查得 | 参与部分唯一键 |
| `version_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 开始时绑定的发布版本 | 读取当时current_version对应快照 | 恢复不切换到新版本 |
| `respondent_key` | string；匹配`^[a-f0-9]{64}$` | 是 | 问卷范围账号关联键 | HMAC-SHA256(secret, survey_id:user_id) | 同问卷匿名/实名一致；非可逆明文用户ID |
| `anonymous` | bool | 是 | 本过程匿名选择 | 开始请求确定 | 已有草稿恢复保持，当前不提供中途切换 |
| `status` | string；值=in_progress,submitted,abandoned | 是 | 填写生命周期 | 初始in_progress | 提交为submitted，放弃为abandoned |
| `raw_answers` | object；键数≤100 | 是 | 受限原始输入映射 | 初始{}；保存可包含未完成或无效值 | 只清除确定跳过的题；提交/放弃清空 |
| `current_question_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 服务器约束的恢复位置 | 初始第一题ID | 保存后按有效路径/首个无效题约束；不是可信客户端游标 |
| `revision` | int/long；数值:1～未额外限制 | 是 | 填写内容乐观并发版本 | 初始1 | 成功保存、提交、放弃递增；与surveys.revision独立 |
| `created_at` | date | 是 | 本过程开始时间 | 开始时now() | 保留 |
| `updated_at` | date | 是 | 本过程最后成功写入时间 | 开始/保存/提交/放弃时now() | 不代表最后一次键盘输入时间 |
| `schema_version` | int/long；值=1 | 是 | 填写过程结构版本 | 应用写入1 | 当前仅支持1 |
| `response_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 否 | 成功提交后的答卷引用 | 提交事务内生成 | 数据库非必需；由应用在submitted时写入，abandoned不写 |

schema允许提交或放弃后的raw_answers仍是对象，但不通过跨字段约束强制其为空，也不强制submitted必须有response_id。这些状态不变量由服务流程、条件更新和事务测试保证，不能把它们写成数据库已经直接保证。

### 4.6 responses

正式答卷只在完整校验成功后追加。answers是包含question_id和value的数组，便于聚合展开，并避免将题目ID直接用作正式答案字段路径。

| 字段 | BSON类型及数据库约束 | DB必需 | 含义 | 应用初值或来源 | 更新与生命周期 |
| --- | --- | --- | --- | --- | --- |
| `_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 正式答卷标识 | 合法提交事务内uid() | 用于回执与草稿关联 |
| `survey_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 所属问卷引用 | 从过程/旧凭证确定 | 统计与权限边界 |
| `version_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 原发布快照引用 | 从绑定过程读取 | 解释题目与答案含义 |
| `version` | int/long；数值:1～未额外限制 | 是 | 发布序号的必要冗余 | 从同一版本文档复制 | 统计直接按整数筛选，由服务保持与version_id一致 |
| `attempt_id` | string；匹配`^[A-Za-z0-9_-]{1,64}$` | 是 | 幂等提交标识 | 新流程为attempts._id；旧流程为签名凭证中的随机ID | 唯一索引防止同过程生成多份 |
| `respondent_key` | string；匹配`^[a-f0-9]{64}$` | 是 | 问卷范围账号关联键 | 同问卷范围HMAC | 匿名与实名共同参与账号去重 |
| `anonymous` | bool | 是 | 正式答卷匿名标志 | 从开始时确定的过程/旧凭证读取 | 提交后不随页面默认值变化 |
| `answers` | array；项数:1～100 | 是 | 实际有效路径上的规范化答案数组 | 由后端evaluate生成 | 只含question_id/value；空可选题为null |

| `schema_version` | int/long；值=1 | 是 | 正式答卷结构版本 | 应用写入1 | 当前仅支持1 |

## 五 问卷定义内部的嵌套结构

### 5.1 definition与draft

两者使用同类定义结构：title（1～200字符）、description（0～5000字符）、allow_anonymous、allow_repeat和questions。草稿允许questions为空；发布定义要求1～100题。草稿可先保存尚未满足业务规则的配置，但请求基础结构与数值边界必须合法，发布时再完整检查。

| 题目字段 | 结构与含义 | 数据库与应用分工 |
| --- | --- | --- |
| id | 稳定字符串ID | DB检查格式；应用检查同问卷唯一、不能为END |
| type | 题型名称字符串 | DB只限制长度；应用注册表判断是否支持 |
| title | 1～500字符题目文字 | DB检查长度；应用拒绝全空白 |
| required | 布尔值 | DB检查类型；作答时只对实际路径执行必答 |
| options | 选项数组，每项id和label | DB约束项目结构与最多100项；应用检查选择题至少2项、选项ID唯一 |
| validation | 题型限制对象 | DB限制已声明字段类型；应用限制不同题型可用字段与可满足性 |
| routing | rules数组与default_target | DB检查基本容器；应用解析条件树与引用关系 |

validation内，min_choices、max_choices、min_length、max_length采用非负整数；min、max采用±10¹⁵内数值；integer_only为布尔。schema没有根据type自动分派所有题型约束，也没有封闭validation所有扩展字段；当前服务使用处理器的allowed_validation拒绝不支持的配置。

### 5.2 四种题型与答案

| 题型 | 配置 | 正式答案 | 草稿原始输入 |
| --- | --- | --- | --- |
| single_choice | 选项、必答 | 已存在选项ID | 暂存字符串或空值，是否合法由后续检查 |
| multiple_choice | min_choices、max_choices | 不重复合法选项ID数组 | 可保存未达到最少数量的数组 |
| text | min_length、max_length | 去首尾空白后的字符串或null | 保留原始输入，允许暂时超出该题长度但不超过草稿上限 |
| number | min、max、integer_only | 合法数值或null | 可保存数字字符串、中间状态“-”或“1.” |

文本最终长度按Unicode码点计算，而不是按UTF-16单元或屏幕字形计数。正式字符串上限10000，草稿字符串结构上限20000；允许较长草稿并不表示可以绕过最终题目限制。JSON数值仍必须有限且绝对值不超过10¹⁵，草稿中的字符串数字解析后也受最终数值限制。

### 5.3 条件树与目标

```json
{
  "all": [
    {"question_id":"q_role","operator":"eq","value":"student"},
    {"any":[
      {"question_id":"q_tools","operator":"contains_all","value":["mongo","python"]},
      {"question_id":"q_age","operator":"gte","value":18}
    ]}
  ]
}
```

上述组合只能放在这些题目已到达的当前位置或后续位置，例如建议题的规则中；如果放到身份题就会非法引用未来题。all为全满足，any为任一满足；未到达、空白或无效值不能满足条件。组合深度最多5，每组1～20项，每题最多20条规则。

rules保持顺序，首条命中目标生效，不命中则default_target；null代表顺序下一题，END代表结束。规则值存入MongoDB，解释器提供固定运算符，不为具体问卷或题号编写特殊分支，不执行eval。

## 六 数据生命周期与状态变化

### 6.1 创建者草稿与发布版本

```text
创建surveys：draft、revision=1、current_version=0
  ↓ 保存定义：替换draft，revision增加
  ↓ 发布事务：插入survey_versions(v1)
              同时设置current_version=1、published、deadline
  ↓ 再编辑：只改变draft，不修改v1
  ↓ 再发布：插入v2并移动当前版本指针
```

关闭把surveys.status改为closed，不删除快照或答卷。发布操作没有把closed当作永久终态，合法再发布可以重新开放。截止时间是问卷级当前状态，不是发布快照的一部分，所以已绑定旧版本的填写也必须服从当前关闭与截止检查。

### 6.2 填写过程与正式答卷

```text
无进行中草稿 → 创建in_progress
                    ├─ 原始输入保存：revision递增，保持in_progress
                    ├─ 完整校验失败：不生成正式答卷
                    ├─ 提交事务成功：responses追加 + submitted + response_id + raw_answers={}
                    └─ 明确放弃：abandoned + raw_answers={}
```

开始与恢复均先找同问卷、同账号的进行中过程，不以匿名选择或新版本另开一份。允许重复填写时，上一过程结束后可以创建下一过程；不允许重复时检查整份问卷历史答卷，不仅检查当前版本。

自动保存采用600ms停顿与最长5秒安排一次请求，网络延迟不在此时间保证内。保存和提交不是两个答案来源：新提交先等最新保存成功，再只携带ID和revision，服务器读库校验。

### 6.3 恢复与清理边界

原始输入经解析和题型校验后产生临时有效值，仅用于规则计算，不另存一份长期副本。progress在第一道无效或未完成必答题停止；保存可以保留尚未完成的后续暂存输入，只清除有效规则已经确定跳过的区间。

服务器约束恢复位置，不能仅相信客户端current_question_id。关闭或截止后的GET仍能读取本人草稿；保存和提交拒绝。已提交或已放弃状态禁止迟到保存，部分唯一索引也随终态释放当前账号的进行中名额。

只有服务器确认保存的内容能够恢复。浏览器关闭前尚未同步内容、故障期间未发出的请求，不保证恢复。当前没有本地持久答案缓存、过程TTL或自动删除进行中内容的政策。

## 七 嵌入 引用与冗余设计取舍

### 7.1 为什么题目嵌入版本

问卷通常以完整定义展示和校验，题目、选项、限制、条件树需要共同解释；随版本复制可以取得一致的一份历史定义。若将每个选项和每个条件节点拆开，获取一份发布问卷需要更多关联与组装，也更容易把旧答案关联到改动后的题目。

代价是定义每次发布会复制，更新草稿可能整体写入，有最大文档大小与定义规模限制。本实现限制最多100题、每题最多100选项，并对请求规模做基础限制；不宣称所有允许配置的笛卡尔组合都一定低于上限。MongoDB单文档16MiB限制仍存在，应用规模限制不能替代真实大小评估。

### 7.2 为什么答卷和草稿独立

responses数量随用户提交增长，不能无限追加到surveys数组；这样可以分别建立统计索引、分页查询，并保持问卷文档有界。attempts与responses分开允许保存无效中间状态，而正式答卷保持干净，不需要每个统计都判断“是否完成”。

本设计减少把所有答卷内容写进同一大文档的问题，但提交仍更新surveys.activity_seq，存在问卷级写竞争；不能因拆集合就声称没有写热点。

### 7.3 冗余逐项审查

| 项目 | 是否冗余 | 用途 | 一致性维护 |
| --- | --- | --- | --- |
| 发布definition与可变draft | 有目的复制 | 保留不可变历史 | 发布事务复制，不随后同步 |
| responses.version及version_id | 是 | 快速筛选和明确引用 | 从同一版本文档生成，应用事务保证对应 |
| responses.path与可推导路径 | 是 | 复核实际执行结果 | 仅后端重算写入 |
| respondent_key跨过程与答卷 | 是 | 重复限制与账号去重 | 同一问卷范围HMAC函数生成 |
| attempts.response_id与responses.attempt_id | 双向关联信息 | 找回回执和过程追溯 | 新流程提交事务共同写入；旧兼容答卷可无草稿 |
| 题目文字复制到每份答卷 | 否 | 避免大量重复和修改不一致 | 通过版本取得原文字 |
| 用户名复制到问卷/答卷 | 否 | 避免与账号不同步 | 使用引用或关联键 |
| 统计缓存计数 | 否 | 避免额外同步维护 | 直接聚合正式答卷 |
| 截止与状态复制到每份快照 | 否 | 保持即时关闭和截止权威性 | 始终检查surveys |

“谨慎冗余”不是完全不复制，而是每项复制有明确来源、写入入口和查询收益。没有必要维护的双份状态不创建；保留的冗余不能由客户端各自填写。

## 八 Schema约束与应用校验的边界

### 8.1 实际约束来源

唯一运行定义为`database/collection_validators.json`，由`database/build_validators.py`生成。启动为新集合使用`validator: {$jsonSchema: ...}`；已有集合必须与目标约束、strict验证级别及error动作一致，否则停止，不能默默覆盖。

responses.answers每项必须恰有question_id与value两个字段（项目设置additionalProperties=false），value允许null、非空字符串、受限数值或非空且元素唯一的选项ID数组。path为非空、最多100且元素唯一的ID数组。数据库不知道这些ID是否真属于绑定版本。

### 8.2 已直接实现的结构检查

| 检查 | DB执行方式 |
| --- | --- |
| 必需字段与基本BSON类型 | required、bsonType |
| 字符串长度、ID/摘要格式 | minLength、maxLength、pattern |
| 题目、选项、答案、路径数量 | minItems、maxItems |
| 路径和正式多选数组元素不重复 | uniqueItems |
| 正式匿名不含user_id，实名必须含user_id | response.oneOf与not/required |
| 状态及当前格式版本范围 | enum |
| 正式数值幅度与基本配置类型 | minimum、maximum |
| 草稿原始输入不含任意嵌套对象 | raw_answers.additionalProperties.anyOf |

### 8.3 仍需应用执行的业务检查

- owner_id、survey_id、version_id和question_id真实存在及引用一致性。
- 题目ID唯一、题型已注册、选项有效、可回答性、数值必须有限。
- 条件字段完整性、运算符与题型匹配、前向引用限制、实际跳转和答案路径一致。
- responses.version与version_id匹配、匿名选择不能中途改变。
- attempts在submitted时关联response_id且清空答案、abandoned清空答案，终态不能再保存。
- 同一问卷禁止重复填写的策略、当前问卷必须开放、截止判断和权限。

顶层对象大多没有additionalProperties=false，保留了字段扩展空间；不应描述为所有未知字段都由MongoDB拒绝。路由condition的数据库约束是非空对象，并未把完整递归条件语义写成JSON Schema；后端解释器是这部分权威检查点。数据库没有通用外键、跨集合唯一关系或文档不可变策略的自动实现。

## 九 索引设计与查询对应

以下11个显式索引逐项来自indexes.json；六个集合还有默认_id索引。这里说明的是设计对应和保证范围，没有运行explain，也不声称实际执行计划、扫描行数或性能提升倍数。


| 集合 / 索引名 | 字段顺序 | 唯一性或特殊选项 | 查询目的和保证 | 代价与边界 |
| --- | --- | --- | --- | --- |
| users / `username_unique` | username_key:1 | unique | 登录按username_key等值查找；注册唯一性；casefold后的字符串唯一，不是用户名展示文本的简单大小写规则 | 每次新增用户维护索引；当前无用户名修改接口 |
| sessions / `session_token_unique` | token_hash:1 | unique | 按令牌摘要认证和退出；摘要唯一，配合服务端expires_at检查 | 不存明文令牌；摘要索引也应限制访问 |
| sessions / `session_expiry` | expires_at:1 | 普通；TTL=0 | 到期会话后台清理；expireAfterSeconds=0表示以expires_at自身作为到期时间 | TTL不是即时执行；逻辑失效由认证查询保证 |
| surveys / `owner_created` | owner_id:1, created_at:-1 | 普通 | owner_id等值过滤并按created_at倒序分页；复合字段顺序对应先筛选后排序的访问模式 | 深页skip仍有代价，未实现游标分页 |
| surveys / `share_unique` | share_code:1 | unique | 通过share_code进入问卷；分享码唯一，避免一链接指向多问卷 | 分享码不代替登录和状态检查 |
| survey_versions / `survey_version_unique` | survey_id:1, version:1 | unique | 读取指定问卷版本，防重复版本序号；survey_id与version组合唯一 | 单独version不唯一；每个问卷均可有v1 |
| responses / `survey_statistics` | survey_id:1, version:1, submitted_at:-1 | 普通 | survey_id与version等值，submitted_at范围筛选；支持统计初始match的字段布局；不是为展开后的题目结果建立索引 | 后续unwind/group仍有计算代价，分页的额外_id排序不承诺完全由此索引覆盖 |
| responses / `attempt_unique` | attempt_id:1 | unique | 按attempt_id找已有回执、防重复插入；同一填写过程最多一份正式答卷 | 不同attempt仍可来自同账号，不能代替禁止重复策略 |
| responses / `respondent_lookup` | survey_id:1, respondent_key:1 | 普通 | 问卷范围内查询账号历史答卷；普通复合查询索引，不是唯一索引 | 允许重复时同键可有多条；禁止重复依赖事务内检查 |
| attempts / `one_active_attempt` | survey_id:1, respondent_key:1 | unique；仅in_progress | 查询/创建本人进行中草稿；unique且仅对status=in_progress文档生效 | 查询包含相同过滤条件；不包含版本和匿名，不绕开进行中限制 |
| attempts / `attempt_owner_updated` | respondent_key:1, updated_at:-1 | 普通 | 已建立的账号关联键与更新时间索引；当前没有跨问卷草稿列表接口，主要恢复查询也不按此字段排序 | 属于可评估的预留索引，维护有成本；不能写成已验证的主要路径加速 |

## 十 并发 事务与原子性

### 10.1 事务基础

`database.transact`使用PyMongo的session.with_transaction，readConcern为snapshot，writeConcern为majority。需要MongoDB副本集；本机用单节点副本集验证事务，不等于有多节点故障容灾。驱动对符合条件的事务错误可以重试，但不保证任意异常都自动成功。

单文档条件更新可原子执行，多集合写入需要明确事务边界。revision属于乐观并发检查，不是数据库全局锁；activity_seq是实际写入协调字段，不是显式锁表指令。

### 10.2 逐操作边界

| 操作 | 实际边界 | 主要检查与修改 |
| --- | --- | --- |
| 保存创建者草稿 | 单文档条件find_one_and_update | _id、owner_id、revision匹配；替换draft并递增revision |
| 发布 | 多文档事务 | 检查revision和完整配置；追加版本；更新指针、状态、截止及协调字段 |
| 关闭 | 单文档find_one_and_update | 所有者；新客户端可携带revision；修改status并递增revision/activity_seq |
| 开始持久填写 | 事务 | 写问卷协调字段；先找已有过程；无则检查开放与重复策略、插入草稿 |
| 自动保存 | 事务 | 检查草稿归属/状态/revision；写问卷协调字段并检查开放；更新原始输入和位置 |
| 放弃 | 单文档条件update_one | 归属读取后以_id/revision/in_progress条件更新，清空内容并转终态 |
| 新正式提交 | 多文档事务 | 已提交则先回原回执；否则检查revision、开放和重复；校验原版本；写答卷并结束草稿 |
| 统计 | 多个聚合读取，不是统一事务快照 | 按版本/时间筛选，按题目分别统计 |

关闭接口兼容旧客户端省略revision，新编辑器会提供；不能写成所有关闭请求都强制带revision。放弃不要求问卷仍开放，也不递增activity_seq，因为其目的是终止本人的未完成过程，主要与保存/提交竞争同一attempt文档。

### 10.3 两页面同时创建

A与B同时进入同一问卷：事务都写同一surveys协调字段，产生冲突并重试；重新读取后可返回已经存在的过程。即使发生插入竞争，部分唯一索引也拒绝第二份进行中草稿，应用捕获重复键后读取已有过程。匿名或当前版本不同不会绕过唯一键。

### 10.4 同一revision同时保存

两个保存都基于revision=2。先成功的事务把草稿更新为3；另一个事务重试后发现revision不符，返回409，不覆盖先成功内容。前端暂停自动保存并保留当前输入，需要明确重新加载。旧响应到达时只确认其发送的快照，新输入仍标为未保存并串行补存。

### 10.5 提交事务的实际顺序

```text
读取并核对本人attempt
  ↓ 已submitted：直接返回关联response的回执
核对in_progress和请求revision
  ↓
更新surveys.activity_seq并检查开放/截止
  ↓
读取绑定版本，按历史策略查重
  ↓
解析原始输入，后端完整evaluate
  ↓
插入responses
  ↓
更新attempts：submitted、response_id、raw_answers={}、revision+1
  ↓
事务提交，返回回执
```

在插入答卷后、更新草稿前发生异常时，事务回滚插入；不能出现一份已保存答卷但草稿仍可再次生成另一份的半完成状态。已执行故障注入测试覆盖这一窗口。

提交成功但响应丢失时，重试先识别submitted并返回原回执，不能先因旧revision报409。responses.attempt_id唯一索引是额外的存储层保护，但不意味着同一账号永远只能有一份答卷。

### 10.6 关闭与提交 保存与放弃

关闭和提交都会修改同一surveys，冲突重试后依据有效先后次序检查状态；先完成提交可以成功，先完成关闭则后提交被拒绝，不采用“点击时间决定”这种无法保证的规则。

放弃与保存/提交写同一attempt。谁先成功会改变状态或revision，另一请求必须重试或被条件拒绝。旧自动保存到达时看到submitted/abandoned，不能把它改回进行中。禁止重复填写的提交也通过问卷级冲突与历史查重协调。

## 十一 查询与统计聚合设计

本章mongosh代码是与实现语义对应的说明示例，不是已执行的explain报告。占位的sid、ver、key、start、end须由实际请求确定，并由后端先验证权限。

### 11.1 问卷列表与恢复

```javascript
// 当前账号自己的问卷列表，实际接口每页20条
db.surveys.find({owner_id: uid}).sort({created_at:-1}).skip((page-1)*20).limit(20)
// 同账号同问卷进行中过程；key由后端HMAC计算
db.attempts.findOne({survey_id:sid, respondent_key:key, status:"in_progress"})
// 已知绑定版本；不是读取最新draft
db.survey_versions.findOne({_id: versionId})
```

列表返回的response_count来自当前页问卷对应responses的分组统计，是所有版本累计份数；详细统计接口省略version时选当前版本。因此列表份数和某个版本的详细统计总数不必相等。恢复查询不是简单按user_id查询attempts，过程里没有该直接字段。

### 11.2 整卷份数与人数

```javascript
db.responses.aggregate([
  {$match:{survey_id:sid,version:ver,submitted_at:{$gte:start,$lte:end}}},
  {$group:{_id:"$respondent_key",n:{$sum:1}}},
  {$group:{_id:null,total:{$sum:"$n"},respondent_count:{$sum:1}}}
])
```

省略时间条件时不限制提交时间；边界均包含。先按账号累计次数，再合计份数与账号组数，避免用一个持续增大的addToSet数组收集所有填写者。没有记录时服务返回0份/0人。

### 11.3 单题有效回答

```javascript
[
  {$match:{survey_id:sid,version:ver}},
  {$unwind:"$answers"},
  {$match:{"answers.question_id":"q_age","answers.value":{$ne:null}}}
]
```

此base后追加人数聚合或题型统计。跳过题没有答案项，可选空题为null，两者都不会进入有效回答。不能仅用整卷份数作每一道题的分母。

### 11.4 单选 多选与去重

单选在base后按`{option:answers.value, person:respondent_key}`分组计次数，再按option汇总count和respondent_count。多选先对answers.value再次unwind，之后使用同一两级分组。

```javascript
[
  {$group:{_id:{option:"$answers.value",person:"$respondent_key"},n:{$sum:1}}},
  {$group:{_id:"$_id.option",count:{$sum:"$n"},respondent_count:{$sum:1}}}
]
```

上面片段前必须接对应题目的base；对多选还需要前述第二次展开。输出按发布版本的选项列表补齐零次选项，不只返回聚合中出现的选项。

默认次数比例为选项count/该题answered；人数比例为选项respondent_count/该题respondent_count。多选比例合计可能超过100%；允许重复填写时，同账号可以在不同次单选选不同项，所以单选的人数集合也可能交叉。人数指去重账号

### 11.5 数值与内容分页

数字题在base后执行`$avg`、`$min`、`$max`，空数据返回null，不把未回答当作0。平均值按有效答案次数计算，不先按人只保留一条。

内容接口同样从筛选和展开开始，按submitted_at倒序、_id升序稳定排序，每页20条，返回value、submitted_at、anonymous以及存在的实名user_id。它不返回respondent_key、attempt_id和会话字段。匿名答卷本来没有user_id；实名输出仍可含user_id，不能笼统写成所有内容查询都隐藏账号。

### 11.6 第三章示例的可复核结果

仅对第三章两条示例按同一v1统计：2份/2个账号；身份student与worker各1次/1人；工具题仅1次有效回答，MongoDB与Java各1次，Python为0；年龄20与40，平均30、最小20、最大40；建议仅“增加实践案例”有效，匿名答卷的null不计入。

这是根据示例推导的结果，不是本机实际测试库的运行输出。真实8用户用例的年龄20～27、平均23.5见第十六部分，两组数字不混用。

## 十二 数据安全 隐私与输出边界

| 数据 | 存储或控制 | 当前边界 |
| --- | --- | --- |
| 密码 | users.password_hash，Argon2 | 不保存或返回明文，示例密码不是业务数据 |
| 登录令牌 | Cookie中随机值，sessions存摘要 | HttpOnly、SameSite=Lax，Secure按环境配置；有效期显式检查 |
| 管理权限 | surveys.owner_id与当前用户匹配 | 不能只凭猜测sid读取他人问卷/统计 |
| 填写草稿 | 通过_id读取后核对问卷范围HMAC键 | 创建者没有读取他人未提交草稿的接口 |
| 匿名正式答案 | 不保存直接user_id，保留问卷范围关联键 | 创建者接口不输出内部去重键；运营者仍可能关联 |
| 配置密钥 | .env或运行环境 | 不进入提交包；不能随意重建而破坏去重与恢复 |
| MongoDB网络 | 本机脚本仅loopback | 当前无认证本机配置不能直接用作公网数据库部署 |

HMAC不是把user_id简单SHA-256，也不是加密用户ID后的可逆存储。相同账号跨问卷的键不同，同问卷匿名与实名键相同。当前没有轮换密钥后读取旧键的版本化方案，不能宣称轮换无影响。

本机课程实现没有完成生产级审计、请求限流、自动备份或多节点故障演练。安全边界应在部署时另行扩展，而不是把这些未验证能力写入本阶段成果。

## 十三 初始化 升级 恢复与第二阶段兼容

### 13.1 普通启动

连接MongoDB并检查副本集 → 全量核对已有目标集合的validator、validationLevel和validationAction → 创建缺少的新集合 → 建立indexes.json中的索引。已有约束不一致时停止，不先覆盖旧库。索引建立也可能因既有重复数据或冲突定义失败，当前不自动清洗业务数据。

### 13.2 显式约束升级

`backend/scripts/upgrade_database.py`提供--check、--apply与--rollback。先校验已有集合约束属于已知旧版或目标版，再统计不符合目标schema的文档；全部通过才保存原约束、目标指纹与进度，逐集合执行collMod。普通异常用日志恢复，进程中断后可显式恢复，恢复前拒绝覆盖其他操作已经改变的约束。

升级在停止业务写入的维护窗口执行，不是在线双写方案。当前演练验证的是初版浅约束到增强约束，不改写业务文档；恢复日志也不能恢复已经删除的业务数据。数据库备份不能用源码压缩包代替。

### 13.3 1.1.0新增attempts

本轮原五集合validator与1.0.2基线一致，新增attempts及索引由初始化创建，不需要重写旧答卷。升级检查区分缺少的新集合与缺少的原核心集合；旧迁移日志仅恢复记录中的集合，不顺带删除后来新增的草稿集合。

兼容的旧凭证式接口仍可处理旧客户端提交，但不提供未完成内容恢复。新流程使用attempts；旧流程的历史responses不必补造attempts。升级前旧页面从未同步的输入无法从数据库恢复。

### 13.4 第二阶段扩展示例

| 未来需求 | 可沿用部分 | 可能调整及验证 |
| --- | --- | --- |
| 新增评分题 | 题型注册、版本快照、答案数组 | 新处理器与统计，检查schema对新答案值形状是否足够 |
| 题库复用 | 发布定义嵌入快照 | 可新增题库引用，发布仍保留当次完整内容 |
| 跨版本统计 | 各版本独立答卷 | 设计稳定语义映射，不能只凭相同题目ID直接合并 |

## 十四 为什么不用关系数据库结构

### 14.1 作业约束与可行性

作业明确要求MongoDB，不允许关系数据库，因此选型首先遵守技术约束。这不表示关系数据库不能实现问卷：关联表、版本表、答案表及JSON列均是可行路线，成熟外键和关系查询也有价值。

### 14.2 为什么不机械照搬完全拆分

若把每个题目、选项、校验字段、条件组与条件叶子都拆成独立集合，再用ID逐层关联，完整问卷读取需要更多查找和组装；发布时还需冻结这些关联对象，否则改动后可能使旧答案失去原含义。本项目主要按完整定义展示、校验和发布，因此没有为了模仿关系表而拆散共同生命周期内容。

| 替代方案 | 可取之处 | 本项目未采用的原因 |
| --- | --- | --- |
| 题目、选项、校验、条件节点全关系式拆分 | 实体复用和关系约束成熟 | 现阶段一起读取与发布，完整树组装成本和历史版本维护复杂度增加 |
| 关系库加JSON列 | 可混合关系实体与嵌套数据 | 技术可行，但违反本作业数据库要求，仍需设计JSON约束与版本策略 |
| 在MongoDB中每字段/节点一集合 | 可按独立节点更新 | 对现有访问模式没有明确收益，增加引用维护和查询组装 |

这里拒绝的是与当前访问模式不匹配的机械组织方式，不是否定引用、唯一约束或事务。MongoDB文档之间仍可使用ID引用；关系数据库也可以存JSON，二者不是“一个能表达嵌套、另一个完全不能”的关系。



## 十五 为什么适合MongoDB

### 15.1 业务形态与能力对应

| 本项目特点 | MongoDB中的对应组织 | 当前实际使用 |
| --- | --- | --- |
| 题型配置多态 | 文档中的对象与数组 | options、validation表达不同形状，但有schema和处理器约束 |
| 规则是组合条件树 | 嵌套文档 | all/any、叶子条件与有序rules，后端有限解释 |
| 一次读取和解释完整问卷 | 定义内嵌题目 | 每份survey_versions携带完整definition |
| 需要保留发布时含义 | 独立版本快照 | 旧过程和答卷引用version_id，不读可变draft解释 |
| 答卷独立增长 | 独立集合和索引 | responses按问卷、版本、时间筛选，不嵌入问卷无限增长 |
| 自动生成统计 | 聚合管道 | match、unwind、group、avg/min/max及去重 |
| 需要原子更新与并发保护 | 条件更新、唯一/部分唯一索引、事务 | revision、唯一过程、幂等、发布和提交一致性 |

### 16.2 本文示例核验

四题完整定义通过实际check_definition；两组答案通过evaluate并比对路径；集合示例离线按当前schema使用的类型、必需字段、数值、数组及oneOf等关键字核对。离线核验不是再次连接MongoDB执行插入，也不是新性能测试，不计入156项业务测试数量。脱敏哈希和ID只用于结构演示。

### 16.3 当前限制

- 引用不是外键，快照不可变主要由API保证；管理员直接写库需要额外权限控制。
- 部分跨字段不变量由应用维护，schema不是完整业务规则引擎。
- 每个过程的自动保存及提交都参与问卷级协调写，存在热点；8用户验证不是负载容量上限。
- 统计多次读取不是严格同一时点快照，内容分页可能受持续新增记录影响。
- 未执行explain和大型数据扫描实验，没有声称所有查询无扫描或完全覆盖索引。
- 单节点副本集不提供多节点容灾；没有分片、在线业务版本2迁移或本地持久恢复缓存。
- schema和请求规模限制仍需与真实文档大小、部署入口限流和备份政策配套。
