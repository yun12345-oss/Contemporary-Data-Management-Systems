基于MongoDB的问卷系统第一阶段项目完成报告

一、项目目标

1.1 任务

实现简化在线问卷系统，使注册用户可以创建、发布和分享问卷，其他用户登录填写，系统执行可配置校验与跳转，保存数据并生成统计。

1.2 用户场景与范围

创建者需要配置不同题型、限制、跳转和开放策略，发布后将链接交给填写者；填写者需要登录、看到明确错误、保存未完成进度并恢复，提交后获得回执；创建者需要按版本和时间查看次数、去重人数、内容与数值统计。

第一阶段包括注册登录、问卷管理、单选/多选/文本/数字、动态跳转、保存恢复、正式提交及统计。文件题、循环问卷、多人共同编辑、跨版本合并、离线持久恢复及公网部署不在当前实现范围。多人同时填写通过真实并发测试验证正确性

二、系统设计

2.1 技术选型与边界

前端Vue3/TypeScript/Vite提供实际操作界面，后端FastAPI/Pydantic提供结构校验和接口编排，PyMongo直接表达文档查询、索引、聚合及事务。

                                           ↓
                                 题型、条件、路径规则
                                           ↓

领域规则不读取用户输入以执行任意代码；服务对权限和数据库编排负责。题型统计使用MongoDB聚合，是实际存储耦合点；没有为了形式分层增加空Repository，后续复杂查询可再提取。

2.3 创建到统计的完整流程

  1. 账号A注册或登录，创建自己的问卷。
  2. 配置四种输入和规则，保存携带revision的draft。
  3. 发布前完整检查，事务追加快照并更新当前指针。
  4. 账号B通过链接登录，开始或继续本人唯一进行中草稿。
  5. 输入按规则显示下一题，自动保存原始内容；退出后恢复原版本和匿名选择。
  6. 提交先同步最新内容，服务端从草稿重算路径并完整校验，事务生成答卷并结束过程。
  7. A按版本和时间查询正式答卷统计，不能读取B未提交内容。
  8. 再发布保留旧含义，关闭和截止保留内容但限制后续写入。

2.4 状态与并发

问卷存储draft/published/closed，截止通过deadline动态判断，不另写一个过期状态。再次合法发布可以重新开放。填写过程为in_progress/submitted/abandoned，后两者清空原始内容且不接受迟到保存。

创建者revision与填写过程revision独立，activity_seq用于事务冲突协调，不能当作答卷数量。部分唯一索引限定进行中过程，attempt_id限定同次提交，禁止重复策略在事务内查历史。

2.5 权限与隐私

所有管理与统计检查owner_id，填写草稿检查当前用户对应问卷范围HMAC键，分享码本身不授权管理。密码Argon2哈希，会话令牌仅存摘要和到期时间。Cookie、Origin和接口权限各有职责，前端路由引导不是唯一防线。

三、MongoDB设计

3.1 为什么这样设计

本模型从数据如何读取、变化和增长出发：账号与会话独立；可变问卷与发布快照分开；题目、选项和规则一起嵌入定义；无界增长的答卷独立；允许不完整的过程不混入正式答案。这样既保持完整版本语义，又能恢复中间输入并独立统计。

每项取舍有代价：发布复制内容，引用完整性由应用维护，自动保存与提交仍写问卷协调字段，存在热点。用schema约束结构、索引保护唯一、revision发现冲突、事务完成跨文档写入，而不是把这些职责混为“MongoDB自动保证”。六集合54字段和11索引的完整依据见详细数据库设计。

3.2 设计出发点与完整模型

本项目按业务访问和生命周期建立六个集合。创建者草稿需要频繁修改，发布版本需要稳定解释历史，填写过程允许不完整，正式答卷需要可统计并持续增长，因此没有将四者混入一个大文档。账号与会话分别管理，所有业务数据和登录会话保存在MongoDB。

完整字段、BSON类型、数据库必需性、应用初值、读写入口、示例与一致性边界，见MongoDB数据库详细设计。该文档展开六集合54字段、11个显式索引以及实际查询和事务；本章集中说明核心设计与理由。

集合 一份文档代表什么 核心字段 生命周期
users 一个账号 _id、username、username_key、password_hash、created_at、schema_version 注册追加，当前无改名或删除接口
sessions 一次登录会话 _id、token_hash、user_id、expires_at 登录追加、退出删除、过期后台清理
surveys 一份问卷当前管理状态 owner_id、share_code、draft、status、deadline、revision、current_version、activity_seq 创建后更新，发布和关闭不删除历史
survey_versions 一次发布快照 survey_id、version、definition、published_at、schema_version、rule_engine_version 每次发布追加，API不提供修改
attempts 一次填写过程 survey_id、version_id、respondent_key、anonymous、raw_answers、status、revision、current_question_id 进行中更新，提交/放弃后清空答案
responses 一次正式提交 survey_id、version_id、version、attempt_id、answers、path、respondent_key、submitted_at 校验成功后追加，参与统计

关系由引用维护：surveys.owner_id指向users，版本引用问卷，草稿和答卷引用版本；提交后的草稿关联response_id。MongoDB没有把这些字符串自动当作外键，没有级联删除或自动存在性检查，相关一致性由应用服务保证。

应用ID实际为24位十六进制字符串；schema允许更一般的1～64位字母、数字、下划线和连字符。时间为UTC的BSON Date，统一毫秒精度。数据库“允许范围”与程序“实际生成值”分别描述，不把示例字符串日期当作真实BSON类型。

3.3 每个集合如何满足需求

users与sessions。 用户名保留展示值，同时按casefold计算username_key并建立唯一索引，避免大小写变体重复账号。密码采用Argon2哈希，不保存明文。会话令牌为安全随机值，sessions只保存其SHA-256摘要；认证同时查询摘要和expires_at。expires_at使用TTL索引清理，但过期拒绝不依赖TTL实际删除时刻。同一账号可以在不同设备拥有独立登录会话。

surveys。 draft嵌入当前可编辑问卷定义，status和deadline是问卷级即时权威状态。revision表示创建者配置版本，保存、发布、关闭递增；current_version指向最新发布序号；activity_seq用于填写、保存、提交及状态变更的事务冲突协调。activity_seq不是答卷计数，普通填写也不会递增创建者revision或更新管理时间updated_at。

survey_versions。 发布时在事务内复制完整draft，并与surveys的版本指针、状态和截止更新一起完成。之后修改草稿不改变已发布快照，旧填写过程和答案仍按原定义解释。version是某份问卷的发布次数，schema_version是文档格式，rule_engine_version是规则语义，三者不能混用；当前后两者只支持1。快照不可变由当前API和服务约定保证，不能说schema阻止管理员直接更新。

attempts。 保存原始输入，允许必答未完成、多选数量不足、数字“-”等状态；解析且通过当前题校验的临时有效值才参与路径判断，不另存一套长期有效答案。每个过程绑定开始时发布版本和匿名选择，服务器重算恢复位置。进行中草稿暂不配置TTL；提交成功后关联response_id并清空raw_answers，放弃后也清空。schema对response_id是可选字段，跨字段的终态清空不变量由服务流程保证。

responses。 只保存完整校验通过的正式答卷，答案采用[{question_id,value}]数组，路径保存有序题目ID。由后端重算决定写入内容，客户端不能指定最终路径。匿名文档不得含user_id，实名必须含user_id；该条件由schema.oneOf直接检查。两者都保留问卷范围HMAC键，支持账号去重与禁止重复策略，创建者接口不返回该内部标识。

3.4 问卷嵌套结构与两种答卷路径

题目包含id、type、title、required、options、validation、routing。单选和多选保存选项；文本保存长度限制；数字保存范围与整数限制。routing为有序规则，条件保存题目引用、运算符、比较值及all/any子树。题目、选项、配置通常整体读取和发布，所以嵌入definition，而不是拆成大量独立条件节点集合。

definition
 ├─ title / description / allow_anonymous / allow_repeat
 └─ questions[]
      ├─ id / type / title / required
      ├─ options[{id,label}]
      ├─ validation{...}
      └─ routing{rules[{condition,target}],default_target}

详细设计的完整四题示例依次为身份、工具多选、年龄、建议：worker跳过工具题；学生同时选择MongoDB与Python可跳到建议；年龄60～120可结束。学生选择MongoDB与Java、年龄20走四题；工作者年龄40走身份/年龄/建议三题。被跳过的工具题没有答案项；路径中的可选建议空白保存null，这两种情况都不贡献该题有效回答。

{
  "answers": [
    {"question_id":"q_role","value":"worker"},
    {"question_id":"q_age","value":40},
    {"question_id":"q_feedback","value":null}
  ],
  "path": ["q_role","q_age","q_feedback"]
}

这是正式答卷局部示意，完整文档必须同时含问卷引用、版本、身份策略、幂等标识和提交时间等必需字段。正式答案中不使用客户端给定的任意动态题目路径；草稿raw_answers虽然是映射，也由服务检查键属于绑定版本。

3.6 数据库约束与应用规则

collection_validators.json约束顶层与嵌套结构，包含字段必需性、BSON类型、ID格式、字符串与数组长度、状态枚举、数值幅度和匿名条件。responses.answers的每项只允许question_id和value，path及正式多选数组检查唯一元素；attempts.raw_answers不允许任意嵌套对象。

数据库没有完整表达题型语义与跨集合引用。题目存在、选项有效、整数区间有解、规则目标向后、真实路径、版本对应、归属、开放状态、重复策略和终态清空，都还需要应用检查。condition在schema中只是非空对象，递归树的完整合法性由解释器判断。

层次 负责内容
请求模型 字段结构、数量、数值安全边界
配置检查 发布完整性、可满足性、引用、规则类型
草稿服务 归属、结构上限、revision、过程状态、位置
提交校验 原版本实际路径上的完整合法答案
MongoDB 基本结构、唯一索引、单文档原子性和事务能力

3.8 状态 事务和竞争处理

创建者保存用_id/owner_id/revision单文档条件更新；发布事务追加快照并移动版本指针；关闭单文档更新并递增协调字段。新填写开始、自动保存和正式提交使用事务，参与同一问卷activity_seq协调；放弃采用过程_id/revision/in_progress单文档条件更新。

提交读取本人过程
  ├─ 已submitted：返回原回执
  └─ in_progress且revision正确
        ↓ 写问卷协调字段，检查当前开放/截止
        ↓ 读取绑定版本并检查历史重复
        ↓ 解析原始输入、重算路径、完整校验
        ↓ 插入responses
        ↓ 更新attempts为submitted、关联response_id、清空内容
        ↓ 事务提交

同时开始时通过事务冲突、已有过程查询和部分唯一索引保证只有一份进行中草稿；同时保存时后到旧revision返回409。提交成功响应丢失的重试先识别终态并返回原回执，避免旧revision误报。插入答卷后发生异常则整个事务回滚。放弃与保存竞争同一过程，终态不接受晚到写入。

关闭与提交按有效事务先后判断：先完成提交可成功，先完成关闭则提交重试后拒绝，不以无法保证的点击时间判断。自动保存也写协调字段，因此热点不仅来自最终提交

3.9 查询 聚合与统计语义

问卷列表按owner_id筛选、created_at倒序，每页20条；恢复按survey_id、问卷范围HMAC键和in_progress查询；版本按绑定_id读取，避免直接使用最新草稿。

统计先按问卷、发布序号和submitted_at范围筛选responses。整卷先按respondent_key累计提交次数，再对组计数得到去重账号数；单题展开answers并过滤题目与null，多选再次展开选项后按“选项+账号”分组。数字执行avg/min/max，空数据为null；内容按提交时间倒序及_id排序分页，匿名不输出直接用户ID。

不使用addToSet收集所有账号到单个大数组。选项统计按版本定义补齐0次选项。次数与人数分别计算，重复填写时单选人数集合也可交叉；平均值按有效作答次数，不是每人一票。attempts从不参与正式统计。

完整示例两份答卷年龄20、40，按示例推导平均30；真实8用户测试是20～27、平均23.5，两组数据不能混写为同一测试结果。

3.10 安全 兼容与扩展边界

respondent_key采用问卷范围HMAC-SHA256，同账号同问卷匿名实名一致，跨问卷不同；不是简单无密钥哈希，也不是宣称运营者完全无法关联。创建者不能读取他人未提交草稿。密钥不入源码包，随意重建会改变去重与恢复标识；当前没有完成无感密钥轮换方案。

普通启动检查已有约束，只创建缺少的新集合并建立索引；显式升级全量预检后保存原约束和目标指纹，逐集合应用，失败按日志恢复。日志不是业务备份；升级在停止写入的维护窗口执行。1.1.0新增attempts时原五集合约束与旧基线一致，旧答卷无需补造填写过程，旧接口仍保留兼容。

3.11 为什么不用关系数据库结构

本项目通常整体读取和发布一份多态问卷及条件树；若把每个题目、选项、限制和条件节点完全拆成独立集合，需要更多关联与组装，并额外冻结这些关联对象才能解释历史答案，因此没有机械照搬全关系式拆分。

3.12 为什么适合MongoDB

题型具有不同options和validation形状，条件具有all/any嵌套树，文档和数组适合表达；发布快照通常整体读取，嵌入共同生命周期的内容保持语义完整；responses独立增长，可按问卷、版本、时间索引和聚合；条件更新、部分唯一索引与事务支撑并发和原子提交。

3.13 设计验证与当前限制

已保存测试覆盖错误文档直接写库拒绝、旧版本解释、5请求开始唯一草稿、revision冲突、终态拒绝迟到写入、关闭只读、事务插入后回滚，以及8账号并发提交后的8份/8人、工具题4次、年龄均值23.5。现有156项业务测试记录不因本次扩写而增加。

文档完整定义及示例答案另经实际check_definition和evaluate离线核对，集合样例按当前schema关键字离线检查，不是新MongoDB插入或性能测试。问卷级协调写有热点、统计不是统一时点快照、部分跨字段约定依赖应用，当前未验证多节点容灾或业务版本2迁移。证据和边界详见数据库设计第十六部分。

四、跳转设计

4.1 规则数据与执行约定

每题保存rules有序数组和default_target，叶子条件含question_id/operator/value，all/any表达组合。单选eq/ne，多选contains_any/contains_all/set_equals，数字比较及闭区间between；文本题不提供跳转运算符。

首条命中立即选择目标，无命中采用默认，null表示顺序下一题，END结束。目标只允许后续题，条件只引用当前或先前题；发布检查ID、选项、操作符、值、引用及深度，不使用eval，不为特定问卷写分支。

4.2 公共推演问卷

使用详细设计教学例：身份q_role→工具q_tools→年龄q_age→建议q_feedback；worker跳年龄；工具同时选mongo/python跳建议；年龄60～120结束；建议默认END。工具恰好2项，年龄0～120整数，建议可空。这与后端测试fixture的q1/q2/q3/q4是不同标签的数据集，不能混用。

建议题可配置all(role=student, any(age>=18, tools包含mongo/python))。年龄被跳过时该叶子不满足，但另一工具叶子可以使any成立。放在身份题则引用未来题，发布拒绝。多条同时为true时只执行最前一条；这项顺序是配置语义，不自动排序“更具体”规则。

4.4 修改答案与服务端重算

从student改worker后工具题确定失效，前后端清除该区间；暂时把前题改成无效输入时，不因路径尚未决定而误删所有后题。恢复位置由服务端有效路径约束，不能凭客户端游标越过未完成题。

4.5 非法配置与验证

回跳、缺目标、重复ID、未来引用、题型不支持运算符、区间顺序错误均拒绝。重排或删除可能使原规则失效，系统提示修正而不猜测业务含义。领域测试验证操作符/组合/路径，前端即时规则与真实提交分别验证；详细步骤和原始索引见测试用例。

五、校验设计

5.1 分层及失败影响

层次 检查内容 失败影响
请求模型 字段、数量、基础类型、额外字段、JSON数值安全 422，进入业务前拒绝
配置发布 完整题目、选项、引用、规则和可回答性 不新增版本、不改变当前有效发布
草稿 本人、状态、revision、原始结构和位置 保留未同步输入，不覆盖他人或终态
正式作答 有效路径必答、题型和值 逐题错误，无正式写入
数据库 基本BSON、唯一/部分唯一索引与事务 拒绝错误结构或冲突，不能替代应用业务校验

5.2 选择题与空值

单选仅接受已存在选项ID。多选值为不重复合法ID数组，最少最多统一表达，固定2项就是min=max=2。可选空值规范null，非空可选答案仍须满足限制。

输入条件 预期
必答单选缺失 拒绝
多选[a,b]且恰好2 合法
多选[a]、[a,b,c]、[a,a]、[a,bad] 数量、重复或选项错误
可选空字符串/空数组/空白 规范为null，不计有效回答
被规则跳过的必答题 不要求回答，不保存该题

5.3 文本与Unicode

去首尾空白后按码点计数，输入组件与Python空白集合保持一致。😀计1，组合字形可含多个码点，不将视觉字形当作统一计数单位。取消原生UTF-16 maxlength，超限原文不截断但阻止非法继续；中文输入法组合完成再更新，避免中间拼音或紧随input重复提交。

5.4 数字与极端值

数值要求有限且幅度≤10¹⁵，先限制再转换，避免超大整数触发OverflowError或BSON编码失败。0与120属于闭区间边界，-1、121越界，18.5违反整数，true不是合法数字。新草稿中的数字字符串按受限语法解析，再执行同样检查；旧正式接口直接传字符串不等同于新草稿解析。

5.5 配置必须存在合法答案

必答多选最多0、必答文本最大0、必答整数范围0.1～0.9均无法完成。发布不仅检查上下界顺序，还检查有效下限和整数点是否存在。合法边界区间0.1～1、-0.9～0、1～1可含整数，不能全部拒绝。

5.6 草稿与正式提交区别

草稿可保存缺必答、数量不足、暂时越界和“-”，以便退出恢复；最多100题、单项字符串20000及基本值结构仍受限。原始输入不直接参与条件。正式提交只读服务器草稿，按实际路径转换并完整校验，清洁答案才进入responses。

5.7 错误与回归

结构details为数组，业务逐题details为对象，客户端按类型读取；页面定位首个错误，失败不产生正式答卷。高级JSON先完整结构/引用检查再替换，损坏组件另有保护。数据库嵌套约束提供最后一层检查，但引用、路径、终态清空等仍由应用维护。边界、无解配置、极端数值、Unicode及输入组件测试保留，不能仅凭函数测试宣称浏览器输入正确。
