# 第二阶段关键逻辑说明

## 一、这份说明讲什么

[系统说明](系统说明.md)介绍怎样操作，本说明解释每次操作背后怎样处理数据、为什么这样处理，以及出错后怎么办。

理解系统时，需要区分三组对象：

| 对象 | 区别 |
|---|---|
| 填写过程与正式答卷 | 前者允许不完整输入，后者必须通过完整校验 |
| 题目系列、版本与问卷实例 | 系列代表一道常用题，版本代表某次固定内容，实例代表它在某份问卷中的具体使用 |
| 题目使用权与统计访问权 | 能把题目放进问卷，不等于能查看相关问卷的答案 |

后文的测试编号可在[逐项测试索引](../3_测试用例/测试证据/逐项测试索引.json)中查找。测试结论沿用已有执行记录，不表示本次整理文档重新运行了全部测试。

## 二、填写、自动保存和正式提交

系统将“正在填写”和“正式答卷”分开保存。半份回答可以恢复，但不会计入正式统计。

### 2.1 自动保存允许不完整输入

填写时，页面先保留原始输入，再同步到服务器。后端检查过程归属、状态、修订号和输入结构，随后根据原发布定义解析答案、计算路径。

数字题输入 `-` 或字母时，可以作为待修正的原始输入暂存，但不能当成有效数字参与条件比较。路径计算遇到第一道无效题时停止，不继续根据该题决定分支。

保存时还要区分两种情况：

- 已经由有效跳转确定绕过的答案会被清理。
- 前题输入无效、尚不能确定后续路径时，后面的暂存输入先保留，修正后重新判断。

只有当前最新修改得到服务器确认，页面才能表示已同步。旧保存请求成功，不代表等待期间的新输入也保存了。

### 2.2 恢复继续使用原版本

填写过程从开始时就绑定一个问卷发布版本。之后题目产生新版、问卷再次发布，都不会让这份过程在中途换题。

恢复时，后端读取原快照和已保存输入，重新计算有效路径及合理位置，不能直接相信客户端提交的位置。问卷关闭或截止后仍可读取已有过程，但会标记为只读，不能继续保存或新增提交。

### 2.3 正式提交必须完整检查

当前可恢复填写流程以服务端草稿为答案来源，提交请求携带过程 ID 和对应修订号。

后端重新检查状态、重复填写策略和实际路径。路径上的必答题或非空答案有错误时，拒绝提交并返回问题；被跳过的答案不写入正式答卷。

检查通过后，在同一事务中：

1. 写入正式答卷和实际路径。
2. 将填写过程标记为已提交。
3. 关联正式答卷 ID。
4. 清除过程中的原始答案副本。

相同过程再次提交时返回原回执，不新增第二份答卷。已提交或已放弃的过程不接受迟到保存。

主要实现：`domain/questions.py`、`domain/rules.py`、`services/attempts.py`。验证包括原有恢复、路径清理、冲突、终态和事务测试，以及 T100 的旧过程跨新发布提交。

## 三、题目修改为什么生成新版本

常用题可能已经被多份问卷使用。如果直接覆盖题目内容，旧问卷和旧答案就可能失去原来的解释依据。因此，每次内容修改都生成新版本。

创建版本前，后端检查所有者、归档状态、修订号、父版本关系和内容是否合法。随后在事务中完成版本号分配、版本插入和最近版本指针更新，任何一步失败都不能留下部分修改。

恢复历史内容也采用新增方式。例如当前为 v3，恢复 v1 内容后生成 v4：

| 字段 | 记录内容 |
|---|---|
| `parent_version_id` | 这次操作的直接父版本，例如 v3 |
| `restored_from_version_id` | 恢复内容来自哪个历史版本，例如 v1 |

v1、v3 本身都不覆盖。版本号表示创建顺序，最近版本也不会自动替换已有问卷。

若其他页面先修改，当前请求返回 409，不擅自更换父版本继续执行。恢复取消不发请求，确认处理期间防止重复操作。

主要实现：`services/questions.py`、`domain/question_versions.py`、`QuestionHistory.vue`。验证包括 T075～T077 和 T218。

## 四、普通保存为什么不能随意修改来源

导入实例会记录题目系列、确定版本，以及这次导入所属的问卷、实例和导入人。来源由后端生成，客户端提交一个 `source` 字段不能证明曾经合法导入。

普通保存时，后端先与数据库原草稿比较来源，再核对来源版本及内容。

| 修改 | 处理方式 |
|---|---|
| 修改必答、顺序和跳转 | 属于问卷实例配置，可以按规则编辑 |
| 保留旧来源，直接修改题干、题型、选项或校验 | 拒绝，内容已与版本不一致 |
| 复制来源到新实例或其他问卷 | 拒绝，原凭据不属于新对象 |
| 保留题目但删除来源 | 拒绝，不能绕过专门解除操作 |
| 删除整道题 | 按正常问卷编辑规则处理 |
| 解除自有题来源 | 通过专门接口检查所有权 |
| 解除或另存他人共享题 | 拒绝，不能转成自有系列 |

前端只读提示帮助用户理解，真正保护在后端。填写者收到的定义会移除内部来源，服务端快照仍保留追溯信息。

主要实现：`question_sources.py`、`surveys.py`、`question_instances.py`。验证见 T078～T090、T092、T098。

## 五、导入和撤销同时发生时怎样处理

导入需要检查问卷修订号、题目状态和当前使用权，再生成新实例、复制内容并写入草稿。

问题在于，授权可能同时被撤销。开始时查到有效，不代表最终写入时仍然有效。只读取授权、写入另一个问卷文档，也不一定与撤销操作发生冲突。

因此，导入和撤销需要触及共同协调记录。发生事务冲突后重试时，重新检查当前授权。

| 成功提交的先后 | 结果 |
|---|---|
| 导入先完成，撤销后完成 | 原实例属于既有合法使用，可以继续保存和发布 |
| 撤销先完成，导入尚未完成 | 导入重新检查后被拒绝，不留下部分实例 |

归档与导入也按对应规则处理。既有使用只属于原问卷中的原实例，不能复制凭据到别处继续新增使用。

主要实现：`questions.authorize_use`、`sharing.revoke`、`question_instances.operation`。T094～T097 检查了两种提交顺序。

## 六、升级预览怎样避免改错题

升级先查看差异，再确认修改。确认必须对应预览对象，不能在用户切题后重新读取当前选中项。

预览保存以下上下文：

- 问卷与实例 ID。
- 原来源版本与目标版本。
- 服务器修订号。
- 本地草稿内容及相关交互状态。

例如，预览 A 后切到 B，原确认立即失效。即使再切回 A，也不能认定期间没有发生变化。编辑草稿、改变目标、关闭窗口或离开页面，同样使旧预览失效；迟到的成功或失败响应不能恢复它。

确认阶段禁止底层顺便自动保存。否则，新保存得到的修订号可能绕过原预览约束。用户应保存后重新预览，再确认。

最终后端仍检查当前授权、同系列关系和修订号。升级保留实例 ID、必答和跳转；如果新版删除选项使规则失效，保留待修复草稿，修复前禁止发布。旧快照保持不变。

主要实现：`Editor.vue`、`useSurveyEditor.confirmQuestionUpgrade`、`question_instances.py`。验证包括 T099、T198～T208、T219、T221。

## 七、更新题库为什么检查目标版本

题库负责个人整理，不能把成员的使用权转授给别人。加入或替换成员时，后端检查题库归属、当前修订号和目标版本权限，并将成员修改与题库修订号更新一起提交。

同库可以保留同系列不同版本，但不能重复加入同一个确定版本。

旧版本不可用，不代表没有可选的新版本。例如 v1 授权撤销、v2 仍有效时，页面应允许打开更新窗口选择 v2。提交时再检查目标授权；若 v2 此时也被撤销，更新失败，原成员保留。

切换题库或成员会关闭旧窗口，清除旧候选并重新加载。更新请求固定原题库、成员和修订号，处理期间限制切换，避免更新错对象。题库成员更新不改变已导入的问卷。

选题器还支持继续加载后续题库，以及在题库内先搜索可读固定版本、再分页，避免遗漏其他页的匹配项或泄露无权查看的标题。

主要实现：`libraries.py`、`Libraries.vue`、`QuestionPicker.vue`。验证包括 T101、T114、T115、T129～T131 和相关组件测试。

## 八、能用题目为什么不等于能看答案

系统分开管理两类授权。

| 授权 | 由谁授予 | 允许什么 |
|---|---|---|
| `use` | 题目所有者 | 采用指定题目版本 |
| `aggregate` | 问卷所有者 | 查询指定问卷、指定版本的汇总统计 |

使用授权不自动包含未来版本、修改、派生、再共享或答卷访问权限。题目作者也不能给自己开放他人问卷的数据。

汇总授权还要求对应问卷实际发布使用过该题目版本。统计接口先确定允许范围，再读取答案，不能先汇总全部数据、最后只隐藏标题。

当前统计授权不开放他人问卷详情、原始答卷或文本原文。只有统计授权的接收者可以从共享记录进入统计，不要求先拥有题目使用权。

主要实现：`sharing.py`、`question_statistics.py`、`question_sources.public_definition`。验证包括 T091、T098、T104、T127。

## 九、使用问卷数为什么不能直接相加

使用追踪分别查询当前草稿、当前发布和全部发布历史，再按问卷 ID 合并。

“历史发布”包含当前发布，因此一份问卷可能出现在多个分类中。发布三次仍然是一份使用问卷，不能按发布次数计数，也不能直接相加分类数量。

可见范围同样受限制：

- 用户可以查看自己的问卷使用明细。
- 题目所有者按权限查看外部脱敏使用数量。
- 他人的私密标题和详情不直接返回。
- 共享接收者通过独立入口查看自己的使用，不调用所有者历史接口。

当前直接查询草稿和发布记录，没有额外维护使用缓存，避免增加同步负担。

主要实现：`question_usage.py`、`QuestionUsage.vue`。T105、T128 检查去重、隐私和接收者访问。

## 十、跨问卷统计怎样保证范围和页面一致

### 10.1 后端先限权，再按版本统计

统计固定一个题目版本，先确定自有或获得有效汇总授权的问卷，再从正式答卷关联发布快照，按其中来源匹配实例答案。

| 指标 | 口径 |
|---|---|
| 有效答卷数 | 按正式答卷 ID 去重 |
| 有效作答数 | 按匹配实例计数，一份答卷可以有多条 |
| 多选比例 | 选项次数除以有效作答条数 |
| 覆盖问卷数 | 包含发布引用该版本但零作答的授权问卷 |
| 有作答问卷数 | 筛选范围内实际收到有效作答的问卷 |
| 时间范围 | 根据正式提交时间筛选，包含起止端点 |

例如，两份答卷包含 20、40、60 三条作答，应得到答卷数 2、作答数 3、均值 40。

时间需包含时区，开始不能晚于结束。数字分组需要 2～30 个严格递增、安全且有限的边界；非法参数被拒绝。不同版本不自动合并，本轮也不提供跨问卷去重人数或文本原文列表。

### 10.2 前端只显示当前查询的结果

v2 请求较慢、用户已切到 v1 时，迟到的 v2 结果不能覆盖 v1。

系统将结果与已应用的查询条件一起保存，只有最新有效请求能够更新结果、错误和加载状态。输入框里尚未应用的新日期，不改变当前结果的范围。

明细保存独立的题目、版本和页码。关闭、换范围或翻页后，旧响应不能重新打开窗口，也不能覆盖新页。最新查询失败时明确反馈，避免把旧数据冒充新结果。

主要实现：`question_statistics.py`、`Statistics.vue`、`QuestionStatistics.vue`。验证包括 T102～T104、T116～T127，以及相关乱序和明细组件测试。

## 十一、旧数据和数据库升级要保留什么

第二阶段兼容旧数据，不要求旧题补齐猜测出来的来源。

| 内容 | 保留方式 |
|---|---|
| 旧题没有 `source` | 继续按原定义填写和统计 |
| 旧填写过程 | 保留原 `version_id`，继续读取原快照 |
| 正式答案 | 保留原格式，不重复增加来源 |
| 旧题另存为常用题 | 只建立当前草稿关联，不自动合并历史答案 |
| 旧代码与修改过程 | 保留第一阶段对照及关键差异、测试证据 |

普通启动检查已有约束、初始化缺失集合和确保索引，不直接覆盖旧校验器。

第一阶段数据库升级时，需要备份、停写和预检，再显式应用目标约束并记录进度。约束修改不能作为一个跨所有集合的业务事务统一撤销，因此恢复日志不能代替完整数据备份。

如果已经产生第二阶段题目或来源数据，程序拒绝只恢复旧约束继续运行旧代码，需要依据维护前完整备份处理。已经处于 2.0.1 的数据库更新到 2.0.2，不需要为本轮程序修复重复迁移结构。

更新还应保留原 `SECRET_KEY`，避免影响已有凭证及相关身份机制。详细步骤见[数据库设计](数据库设计.md)。

主要实现：`database.py`、`migration.py`、迁移脚本及来源兼容逻辑。T100、T106～T108 等记录验证了旧过程、历史关联边界和升级保护。
